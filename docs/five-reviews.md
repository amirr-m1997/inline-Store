# بازبینی پنج‌گانهٔ سایت مشتری مهراصل (فروشگاه B2B)

**تاریخ:** ۱۵ مهر ۱۴۰۵ · **پروژه:** `mehrasl-panel` (Django 5.2 + Unfold) · **مخزن:** دو کامیت روی `main`
**دامنهٔ بازبینی:** فروشگاه مشتری (اپ `shop`) + نقاط برخورد آن با پنل مدیریت
**مخاطب:** تیم فنی — همه‌ی یافته‌ها با «اقدام انجام‌شده» یا «اقدام پیشنهادی» مشخص شده‌اند.

### چطور ببینیم و اجرا کنیم

```bash
# ۱) سایت مشتری (بدون ورود خودکار پنل) — مرورگر: http://localhost:8000/
PANEL_DEMO_AUTOLOGIN=0 python3 manage.py runserver 0.0.0.0:8000

# ۲) پنل مدیریت (با ورود خودکار دمو)
PANEL_DEMO_AUTOLOGIN=1 python3 manage.py runserver 0.0.0.0:8000     # → /admin/

# ۳) بازبینی بصری رنگ در هر دو تم (فایل خودبسنده، بدون نیاز به اینترنت)
python3 scripts/build_shop_preview.py     # → /home/user/mehrasl-shop-preview.html

# ۴) آزمون‌های تکرارپذیر
python3 scripts/storefront_check.py     # ۱۰۴ بررسی سرتاسری مشتری
python3 scripts/security_audit.py       # ۵۹ سناریوی حمله
python3 scripts/theme_contrast_check.py # WCAG هر دو تم
python3 manage.py panel_check           # ۳۷ بررسی پنل
python3 manage.py check --deploy        # هشدارهای محیط عملیاتی
```

**حساب‌های آزمون:** مشتری تأییدشده `cu0-admin` / `Mehr@1405` — مشتری در انتظار تأیید `cu9-admin` — مشتری مسدود `cu12-admin` — ادمین `admin` / `Mehr@1405`.

## ۲) بازبینی «به‌عنوان برنامه‌نویس»

**یافته‌ها و اقدام‌ها**

1. **کد مرده و تکراری در سبد** — `is_empty` و `distinct_count` هیچ‌جا استفاده نمی‌شدند → حذف شد. `count` سربرگ به `safe_stored_qty` منتقل شد تا یکجا از session دفاع شود.
2. **ناهمگونی سبک واردکردن** — `views.py` از `forms as shop_forms` و `urls.py` از `from .forms import LoginForm…` استفاده می‌کرد → یکدست شد.
3. **هک `__import__()` در نسخهٔ اول `urls.py`** → با واردکردن صریح جایگزین شد (همین پنجره).
4. **منطق تجاری داخل نما** — محاسبهٔ اعتبار و ساخت سفارش+فاکتور مستقیم در `checkout()` بود → به لایهٔ سرویس منتقل شد:
   `shop/services.py::credit_snapshot / over_credit / place_order` (نما فقط اعتبارسنجی فرم و پاسخ HTTP).
5. **آداپتور `_Row`** برای تبدیل dict سبد به شکل مورد انتظار `create_order` — باقی مانده است؛ گزینهٔ جایگزین (بازمحاسبهٔ `Cart.rows()` به `LinePreview`) به‌عنوان بدهی فنی مستند شد، چون قالب‌ها در حال حاضر از dict استفاده می‌کنند و تغییرش بدون بازنویسی قالب‌ها ارزش عملی کمی دارد.
6. **قالب‌های بدون وابستگی بیرونی** — استایل‌های Tailwindی داخل فرم‌ها (`class="w-full rounded-xl…"`) کد مرده بودند (CDN نداریم) → به کلاس بومی `form-input` تغییر کرد و CSS سایت تنها منبع ظاهر شد.
7. **ظرفیت آزمون** — سه اسکریپت آزمون مستقل نوشته شد که روی **پایگاه‌دادهٔ آزمون** اجرا می‌شوند و به دیتای دمو دست نمی‌زنند (`create_test_db` + `seed_demo` + تخریب در پایان): `storefront_check.py`، `security_audit.py`، `theme_contrast_check.py`.
8. **کپیرایت رنگ‌های نمودار** — `#94a3b8` (کنتراست ۲٫۷:۱) در `core/analytics.py` → `#64748b`؛ هم‌راستا با سایر نقشه‌های رنگ وضعیت.
9. **آزمون‌های هر دو سطح** — `panel_check` (۳۷/۳۷)، `check_panel_js` (۲۱ بررسی)، `check_panel_dom` (jsdom، شامل تبدیل تاریخ شمسی) بعد از هر تغییر سبز ماندند.

**بدهی فنی باقی‌مانده (مستند):** آداپتور `_Row`؛ یکسان‌سازی `cart.rows()` با `LinePreview`؛ انتقال پیام‌ها از `messages` به یک لایهٔ notification اگر بعداً API موبایل اضافه شد.

## ۳) بازبینی «به‌عنوان هکر»

**آسیب‌پذیری‌های واقعی که پیدا و رفع شد**

| شدت | یافته | بهره‌جویی ممکن | اصلاح |
|---|---|---|---|
| **بالا** | ورود خودکار دمو روی مسیر `/` (که اکنون فروشگاه است) هر بازدیدکننده را با حساب **ادمین** وارد می‌کرد؛ کاربر ادمین `is_staff` است و در نتیجه `_require_invoice_access` برایش باز می‌شد | دسترسی ناشناس به داده‌ی سازمانی و پنل | شرط میدل‌ور به `/admin` محدود شد + بررسی خودکار در `security_audit` |
| **متوسط** | Open Redirect در `cart_add` با پارامتر `next` (`//evil.com`) | فیشینگ با دامنهٔ معتبر مهراصل | اعتبارسنجی با `url_has_allowed_host_and_scheme` |
| **متوسط** | خروج با GET (اجبار کاربر به خروج از حساب با `<img src>`) | مزاحمت/DoS کوچک برای مشتری | `@require_POST` |
| **متوسط** | ورودی تعداد بسیار بزرگ → `InvalidOperation` و خطای ۵۰۰ | DoS سبک با یک POST | سقف تعداد + پاک‌سازی ورودی + مقاوم‌سازی قالب‌بندی عدد |
| کم | فقط `MinimumLength(6)` برای گذرواژه | حدس آسان گذرواژه | ۸ نویسه + Common + Numeric + Similarity |
| کم | پرداخت شبیه‌سازی‌شده بدون نگهبان محیطی | تسویهٔ جعلی فاکتور در صورت فراموشی خاموش‌کردن پرچم | بررسی `shop.W001` در `check --deploy` + مسدودکردن خودکار مسیر پرداخت وقتی پرچم خاموش است |

**آنچه آزمون شد و سالم بود (۵۹ سناریو، ۰ ناموفق)**

- **CSRF:** POST بدون توکن به سبد/ورود/خروج → `۴۰۳`؛ متدهای PUT/PATCH/DELETE → `۴۰۵`.
- **احراز هویت:** همهٔ مسیرهای خصوصی برای مهمان → ریدایرکت به `/accounts/login/?next=…`؛ پنل ادمین برای مشتری → `۳۰۲`.
- **IDOR (افقی):** سفارش/فاکتور/پرداخت/حذف نشانی شرکت دیگر → `۴۰۴` (همهٔ کوئری‌ها با `company=membership.company` قید شده‌اند).
- **تفکیک نقش:** کاربر «بدون مجوز مالی» فهرست صورت‌حساب را نمی‌بیند و به فاکتور/پرداخت دسترسی ندارد.
- **دست‌کاری قیمت:** سبد فقط `{pk: qty}` ذخیره می‌کند؛ شناسهٔ جعلی در session → «کد ناشناس» و حذف از جمع‌ها؛ ارسال `unit_price/company/status/discount_pct` در فرم ثبت سفارش بی‌اثر است.
- **تزریق:** `' OR 1=1--`، `'; DROP TABLE…`، نویسهٔ تهی، `<script>` بازتابی → مهار؛ شمارش محصولات سالم.
- **جعل در ثبت‌نام:** ارسال `is_staff/is_superuser/kyc_status/credit_limit` → بی‌اثر (KYC در `pending`، اعتبار `۰`).
- **حدس گذرواژه:** پس از ۵ تلاش ناموفق قفل موقت (کش، ۵ دقیقه)؛ پیام فارسی.
- **نشست:** شناسهٔ نشست پس از ورود تعویض می‌شود (Session Fixation)؛ کوکی `HttpOnly`، `SameSite=Lax`؛ `X-Frame-Options: DENY`؛ `nosniff`.
- **هدرها:** در production هدر `X-Frame-Options: DENY` و میدل‌ور فعال است؛ در محیط پیش‌نمایش هیچ هدر فریم‌بندی فرستاده نمی‌شود تا سایت داخل iframe باز شود.
- **افشا:** بازیابی گذرواژه برای ایمیل ناموجود و موجود پاسخ یکسان می‌دهد؛ خطاها مسیر سرور را لو نمی‌دهند؛ `/.env` و عبور از مسیر استاتیک بسته است.

**ریسک‌های پذیرفته‌شده (با توجیه و اقدام پیشنهادی)**

1. **پیام «این ایمیل قبلاً ثبت شده است» در ثبت‌نام** → افشای وجود حساب. *پذیرفته* چون بدون آن جریان ثبت‌نام سازمانی برای کاربر گیج‌کننده است؛ اگر لازم شد، به «اگر این ایمیل متعلق به شماست، وارد شوید» تبدیل کنید.
2. `DEBUG=1` پیش‌فرض در توسعه → در تولید باید `DJANGO_DEBUG=0` و `DJANGO_SECURE=1` تنظیم شود (هر دو در `check --deploy` دیده می‌شوند).
3. `MEDIA` فقط در `DEBUG` سرو می‌شود؛ در تولید باید وب‌سرور/CDN یا S3 باشد. (فایل‌های بارگذاری‌شده فعلاً فقط اسناد فنی پنل هستند.)
4. بدون 2FA/انقضای گذرواژه؛ برای مشتریان سازمانی بزرگ در نقشهٔ راه بگذارید.

## ۴) بازبینی «به‌عنوان مهندس نرم‌افزار»

**معماری فعلی (لایه‌ها)**

```
config/            تنظیمات، URLها (فروشگاه روی «/» ، پنل روی «/admin/»)
shop/              سایت مشتری: cart.py · forms.py · views.py · services.py · checks.py · urls.py
                   templates/shop/** (RTL) + static/css/shop.css + static/js/shop.js
orders/services.py لایهٔ مشترک: prepare_lines() و create_order()  ← هم پنل، هم فروشگاه
pricing/services.py  resolve_price() و price_levels_for()
inventory/services.py stock_check()   finance/services.py register_payment()
```
**تصمیم کلیدی:** سبد هیچ قیمتی ذخیره نمی‌کند؛ هر رندر قیمت را با `resolve_price` برای همان شرکت بازمحاسبه می‌کند. نتیجه‌اش هم امنیت (دست‌کاری قیمت بی‌اثر) و هم «یک منبع حقیقت» با پنل است.

## ۷) کارهای باقی‌مانده که به شما نیاز دارد

1. **درگاه پرداخت واقعی:** کلید و نام درگاه (زرین‌پال/سامان/پارسیان) تا `SHOP_MOCK_GATEWAY=0` شود.
2. **ایمیل:** نشانی SMTP یا سرویس تراکنشی برای «فراموشی گذرواژه» و اعلان سفارش.
3. **فاکتور رسمی:** قالب PDF با مهر/امضا و اتصال سامانهٔ مؤدیان (شناسهٔ یکتای مالیاتی).

5. **دامنه و HTTPS:** `DJANGO_ALLOWED_HOSTS`، `DJANGO_SECURE=1` و `CSRF_TRUSTED_ORIGINS` برای دامنهٔ نهایی.
6. **بازبینی چشمی رنگ:** اگر در فایل پیش‌نمایش جایی را می‌پسندید/نمی‌پسندید بگویید تا پالت را تنظیم کنم (همه‌چیز روی متغیرهای CSS متمرکز است و یک‌جا تغییر می‌کند).
